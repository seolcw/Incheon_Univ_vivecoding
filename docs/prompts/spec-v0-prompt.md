너는 오전 10시부터 오후 3시까지의 바이브 코딩 대회에 나가는 팀(총 3명)의 설계 담당이다.
아래 입력으로 파일 3개를 만든다.

1. `docs/SPEC.md`: 1차 설계 문서 (SPEC v0)
2. `contracts/api.md`: 프론트와 백엔드가 지킬 API 명세
3. `docs/prompts/pro-spec-v1.md`: GPT Pro에 그대로 붙여넣을 구체화 요청 프롬프트

---

## 입력 1. 대회 브리프 [필수]

[주제]
- 주제 : Ai로 다시 쓰는 대학 생활
- 예시 : Ai 캠퍼스 사주풀이, 교수님과 나의 궁합
- 부제 : 문제 해결을 넘어, 새로운 경험을 만드는 창의적인 웹

[평가 항목]
- 창의력 (20점): 아이디어의 참신성 및 학교 문제 해결성
- AI 활용 능력 (15점): AI 툴 활용도 및 프롬프트 로그 우수성
- 결과물 완성도 (15점): 서비스 작동 여부 및 시연 명확

[규칙]

1. 개발 및 발표 시간 준수 (10:10~15:00)
- 참가자는 정해진 개발 시간 내에 개발과 발표 및 시연 준비를 모두 완료해야 합니다.
- 개발 마감 시간을 반드시 준수해야 합니다.
2. 참고 코드 출처 명시
- 코드를 참고하거나 활용한 경우 출처를 명확히 밝힙니다.
3. 규칙 위반에 따른 책임
- 위 규칙을 준수하지 않아 발생하는 불이익에 책임은 참가자에게 있습니다.

## 입력 2. 아이디어 메모 [필수]

- 한 줄 요약: 학교 빈 강의실 추천 알림 서비스
- 대상 사용자와 불편함: 도서관 스터디룸 부족, 강의 시작 전 해당 강의실에 미리 가있고 싶은데 앞시간에 강의가 있는지 에브리타임으로 매번 확인해야 함.
- 꼭 할 기능 (3개 이내, 기능마다 입력 → 결과 → 완료 기준):
  1. 학교의 빈 강의실 확인
  2. 빈 강의실에 원하는 목적으로(ex.카공 모여라) 모임을 만들고 원하는 사람끼리 약속을 하는 서비스
  3. 빈 강의실 정보를 시각화해서 학교 캠퍼스로 보여준다 (가능하면 층별 구현까지)
  4. Ai 챗봇으로 추천 서비스 제공(GPS 기반 사용자 위치를 추적해서 주변에 알맞는 강의실 추천 등)
- 데모에서 보여줄 장면: 위 1,2,3번 기능 시연. 가능하면 4번 기능까지.

## 입력 3. 팀과 환경 [기본값, 바뀔 때만 수정]

- 역할
  - 프론트 1명: Mac, Claude Code. 화면 전체와 데모 조작
  - 백엔드 A: Windows, Codex. CRUD API, DB, 배포
  - 백엔드 B: Windows, Codex. AI 기능, 핵심 로직, GPT Pro 운영, 발표 자료
- 스택 (기본): Next.js + TypeScript + Tailwind + shadcn/ui / FastAPI(Python) + Firebase(Firestore, 필요하면 Auth) / 배포 Vercel + Render
- 백엔드 언어: Python이 기본이다. 백엔드 2명은 유니티 개발자라 C#에 더 익숙하다. 주제상 C#(ASP.NET Core)이 뚜렷하게 낫다고 판단하면 C#으로 정하고 이유를 "기술 결정"에 적는다. Firebase는 어느 쪽이든 유지한다.
- 구현 시간: 10:45–16:00
- 체크포인트: 10:45 API 명세 고정 / 12:00 첫 배포 / 13:30 핵심 흐름 동작 / 15:00 기능 추가 중단 / 16:00 코드 수정 중단 (제출 마감이 16:00이면 코드 수정 중단과 영상 녹화는 15:30)
- 발표: {{5}}분
- 저장소: 폴더 `frontend/` `backend/` `contracts/` `docs/` (각자 담당 폴더만 수정), 브랜치 `fe` / `be-a` / `be-b`, 1시간마다 main에 합침
- API 규칙: 경로 `/api/...`, JSON camelCase, 날짜 ISO 8601, 에러 `{"error":{"code","message"}}`
- 저장소에 AGENTS.md가 있으면 그 규칙이 이 프롬프트보다 우선한다.

## 작성 규칙

- **범위:** 아이디어 메모의 "꼭 할 기능"이 MVP다.
  - 기존 기능 보완은 MVP 완료나 데모를 막는 문제에 한정해 넣는다. 새 화면, 엔티티, 외부 서비스 없이, 보완 작업 전체 합계 30분 이내여야 한다.
  - 완전히 새로운 기능은 넣지 말고 "시간 나면" 목록에만 적는다.
- **정확도:** 데이터 모델과 API 명세는 필드명과 타입까지 정확하게 쓴다. 엔드포인트마다 요청·응답 JSON 예시를 하나씩 둔다.
- **분량:** 화면 디자인과 내부 구현은 간단하게. SPEC.md는 팀이 15분 안에 읽을 분량(A4 2쪽 내외)이다.
- **기술 결정:** 기본 스택은 바꾸지 않는다. 백엔드 언어(Python 또는 C#)와 그 밖의 기술 선택(라이브러리, 폴더 구조, 상태 관리, AI 호출 방식 등)은 네가 결정해서 "기술 결정" 섹션에 적는다.
- **엣지 케이스:** 데모 시나리오에 나오거나 핵심 흐름을 멈추게 하는 것만 다룬다.
- **질문 금지:** 되묻지 않는다. 모호한 부분은 가정하고, 가정 목록을 맨 앞에 적는다.
- **검토는 한 번:** 다 쓴 뒤 데이터 모델, API 명세, 담당 분배의 필드명과 엔드포인트가 서로 일치하는지만 확인하고 끝낸다.

## 산출물 1. `docs/SPEC.md`

0. 가정 목록
1. 한 줄 요약, 대상 사용자, 심사기준별 어필 포인트, 제출 정보(마감, 제출물, 제출 담당)
2. 기능 목록: MVP는 기능마다 완료 기준을 적고, "시간 나면"은 우선순위 순으로
3. 화면 목록과 데모 시나리오 (발표 시간 기준 순서)
4. 데이터 모델: Firestore 컬렉션 구조, 필드와 타입
5. API 요약: 엔드포인트 목록 표만 두고 "전문은 contracts/api.md"라고 적는다
6. 담당 분배: 사람별 담당 폴더와 체크포인트에 맞춘 시간대별 작업
   - 백엔드 B가 수정할 핵심 로직 폴더를 경로로 명시한다 (AGENTS.md의 be-b 수정 범위가 된다)
   - 백엔드 A의 첫 배포는 12:00 전에 끝나도록 10:45–12:00 구간에 둔다
   - 최종 배포, 영상 녹화, 제출이 제출 마감 전에 끝나도록 둔다
7. 안 할 것
8. 구현 위험 요소와 대응
9. 기술 결정: 항목마다 결정 / 이유 한 줄 / 대안 하나

## 산출물 2. `contracts/api.md`

- 공통 규칙 (Base URL 환경 변수, 경로, 날짜, 에러 형식)
- 에러 코드 표 (code, HTTP 상태, 언제)
- 엔드포인트마다 요청 JSON, 응답 JSON, 가능한 에러 코드
- AI 기능이 있으면 AI 출력 JSON 스키마

## 산출물 3. `docs/prompts/pro-spec-v1.md`

GPT Pro는 이 저장소도, 이 대화도 모른다. 이 파일 하나만 붙여넣어도 이해되는 프롬프트로 만든다. 아래 틀을 채우되, `[다듬을 것]`은 네가 쓴 v0에서 가장 약하다고 판단한 부분 3~5개로 구체적으로 적는다. 파일에는 이 틀을 코드 블록으로 감싸지 말고 본문 그대로 쓴다. (SPEC 안의 JSON 코드 블록과 겹쳐 깨지지 않도록)

```
[목표]
아래 SPEC v0을 구현 직전 수준의 SPEC v1으로 구체화해 줘.
팀은 이미 v0의 API 명세로 구현을 시작했다.

[상황]
(대회 주제, 조건, 심사기준과 배점, 일정을 5줄 이내로 요약)
(인원과 역할, 스택, 체크포인트)
지금 시각 10:30, 구현 마감 16:00

[제약]
- API 계약(경로, 메서드, 필드명, 타입, 필수 여부, 응답 구조, HTTP 상태)은 바꾸지 말 것. 바꿔야 한다고 판단하면 본문에 넣지 말고 '계약 변경 제안'에 따로 적을 것
- 스택과 v0의 '기술 결정'은 유지할 것. 문제가 있으면 proposals에만 적을 것
- 기존 기능 보완은 MVP 완료나 데모를 막는 문제에 한정하고, 추가 작업 시간은 전체 합계 30분 이내. 넘는 것은 위험 요소로 보고할 것
- 완전히 새로운 기능과 선택적 개선은 본문에 넣지 말고 proposals에만
- 엣지 케이스는 데모에 나오거나 핵심 흐름을 멈추게 하는 것만
- SPEC v1은 v0의 1.5배 분량 이내로 쓸 것

[다듬을 것]
(v0에서 가장 약한 부분 3~5개. 예: AI 출력 스키마와 실패 처리, 상대 날짜 해석, 데모용 시드 데이터)

[출력]
1. 가정한 내용 목록 (되묻지 말고 합리적으로 가정)
2. 반드시 고칠 것 (v0 대비, 최대 7개, 중요도 순)
3. SPEC v1 전문
4. 계약 변경 제안 (없으면 "없음". 사람이 승인하기 전에는 반영하지 않는다)
5. proposals.md 전문 (제안마다 내용 / 심사기준 효과 / 예상 시간 / 필요 조건 / 위험)

[SPEC v0]
(docs/SPEC.md 전문)

[API 명세 v0]
(contracts/api.md 전문)
```

## 마지막 보고

파일 3개를 저장한 뒤, 채팅에는 아래 세 가지만 적는다.

- 저장한 파일 경로 3개
- 가정 중 사람이 확인해야 할 것 (최대 3개)
- Pro에 넘기기 전에 사람이 정해야 할 것 (없으면 "없음")
